# 操作とトランザクション

## 共通契約

呼出元の本人・管理者権限はAPIがトークンから検証する。要求の `subject` や管理者フラグを信用しない。
以下の主体は検証済みコンテキストであり、顧客向けの読取り・更新は必ず所有者条件をSQLに含める。
該当しない注文・住所・オファー・かごは存在を漏らさず0件／NOT_FOUNDにする。管理照会は管理者専用。
ビューはアクセス制御境界ではない。顧客向け応答には原価、粗利、他顧客の識別子を含めない。

分離レベルはREAD COMMITTED。書込みは一つのローカルトランザクションで行う。
ロック取得後に状態・在庫・値を読み直す。コミット後の結果だけを成功として返す。
ロック待ち中の一覧の値を、そのまま更新可否の判断に使わない。

APIとの境界ではbigintのIDは10進文字列、金額は小数2桁の10進文字列、数量は整数、日時はUTCのRFC 3339、予定日はYYYY-MM-DDとして扱う。
モデル上の操作名は業務契約を表すもので、HTTPパスやJavaの型の追加ではない。既存アプリケーションAPIはこのリポジトリに存在しない。

複数種類を触る操作のロック順は、**冪等記録→顧客→かご(UUID順)→住所(ID順)→オファー(ID順)→注文(ID順)→書籍(ID順)→現在在庫(ID順)**。
必要な種類だけをこの順序で取得する。イベント・状態表は対象オファー／注文／書籍のロック下で更新する。
同じ注文内の複数書籍は書籍ID昇順。書誌・売価更新も書籍行をロックし、注文時の価格取得と直列化する。
通常操作が現在状態だけを先にロックしてから親をロックする実装は禁止する。

| 操作 | 入力 | 成立条件・同一取引内の効果 | 結果 |
| --- | --- | --- | --- |
| 氏名同期 | 検証済みsub・姓・名 | 顧客をUPSERT。同じsubへの初回ログイン競合はPKで統合。メール・パスワードは保存しない | 主体 |
| 住所登録・更新・無効化 | 本人・住所ID・住所値 | 本人条件、米国住所形式。無効化後も行を残す。注文スナップショットは更新しない | 現在の本人住所 |
| かご投入・数量編集・削除 | 本人または未ログインCookie・書籍・種別・数量 | かごをロック、購入種別の新規／変更数量は最新在庫以下。欲しい物は在庫を予約しない。変更ごとにrevisionとupdated_atを更新 | かご・現在の税込額 |
| 欲しい物→購入へ移動 | かご・対象書籍または全件 | かごと書籍をロック、購入側は重複数量の最大値。在庫不足の対象は欲しい物に残して通知、移動可能な対象を購入へ移す。移動したWISH行だけを削除 | 移動した対象と残った対象 |

| 注文確認 | 本人・かご・配送先 | 購入明細と現在価格・在庫を読み、在庫0の明細を除外して書名を明示。除外明細は削除しない。全件除外なら注文不可 | 確認結果 |
| PLACE_ORDER | 本人・確認結果・住所ID・キー | 下記確定手順。最低1明細、選択数量を全件確保できること | 注文ID・番号・税込合計・予定日・明細 |
| ACCEPTED／SHIPPED／DELIVERED | 管理者・注文ID・キー | 注文をロック、要件の直前状態だけを許可。イベント追記と状態更新。在庫は変更しない | 確定状態 |
| CANCELLED | 本人・注文ID・キー | 本人注文をロック、PENDING／ORDEREDだけ。全明細を一度だけ返却、取消イベント・在庫移動・現在状態・結果を一括確定 | 取消済状態 |
| SUBMIT_OFFER | 本人・書誌・分類・希望価格・キー | 価格1〜1,000,000、分類整合。申込とSUBMITTED、初期状態を一括保存 | オファーID |

確認結果はAPIが生成し、主体・かごID・revision・購入対象(書籍ID、数量、税抜現在単価)・除外書籍・住所IDを含める。
将来のAPIはこの内容へHMAC-SHA256署名を付け、15分の有効期限を検証する（設計仮定）。署名鍵は実行時構成で取得する。
クライアントが提示した任意の購入対象や除外理由を、そのままAPI生成の確認結果として受け入れない。
DB検証用コードは検証済み確認結果を入力とし、署名・トークン検証・画面の動作を実装しない。
かごCookieはSecure・HttpOnly・SameSiteを付け、ログイン後の所有者判定には必ずsubを使う。顧客かごのUUIDを未ログインCookieとして再利用しない。

## 注文確定の原子性

1. 本人のキーで冪等判定する。既存成功なら同じ結果を返す。
2. 本人の顧客・かごをロックし、確認時のrevisionと一致することを検査する。住所を本人・有効条件でロックする。
3. 確認済みの全対象書籍をID順にロックする。現在の購入明細・数量・価格と確認結果を照合し、最新在庫が数量以上か再検査する。
4. 税抜小計→税→合計を計算する。注文日時はAPIのUTC時計。注文明細へ売価・原価を、注文へ住所値と合計・予定日をコピーする。
5. 注文・最低一明細・PLACED・初期状態を保存する。各書籍にORDERED移動を追記し現在在庫を同量減らす。
6. 確定した購入明細だけをかごから削除し、revision・更新時刻を更新する。除外購入明細と欲しい物は残す。
7. 冪等結果を保存してコミットする。

確認後に在庫不足や価格変更があれば途中で一部だけを確定せず、全体をロールバックして再確認を促す。
確認時に在庫0だった明細を、確定直前に在庫が戻ったため無断で注文に追加することもしない。
数量不足を残数へ切り詰めず、合意した数量を全件取れるかで判断する。
かごの明細をロックだけでなくrevisionで照合するため、別端末での数量編集・統合も再確認対象となる。

## 取消・棚入れの重複と競合

取消と出荷は同じ注文行のロックを取得する。先に出荷した場合は取消を拒否し、先に取消した場合は出荷を拒否する。
取消の在庫移動は元注文イベントと元注文明細を参照する。一意性で同一注文の同じ書籍の二重返却も防ぐ。
取消は販売側の返金を意味せず、販売側の支払記録を作らない。

棚入れは同じオファー行をロックする。STOCKEDイベントの一意性と `book_receipt.source_offer_id` の一意性を併用する。
同じキーの再送は前の書籍IDを返し、別キーの二度目の棚入れは業務重複として拒否する。
書籍の編集で取得原価を書き換えず、別原価で取得した本を既存書籍IDの在庫増として混ぜない。

## 冪等性と失敗

冪等キーは(検証済み主体、操作名、ランダムUUID)。内容はサーバが型検証・正規化した業務引数からSHA-256を計算する。
オブジェクトのキー順を固定し、明細は書籍ID順、金額は小数2桁、日時はUTC表現へ揃える。
発行時刻・トレースID・署名・有効期限などの配達情報は内容ハッシュから除く。支払の実際の時刻は業務引数として含める。
同一キー・同一内容は保存済み結果、同一キー・異内容は競合。記録は無期限保持する。

`command_receipt` は取引の先頭でINSERTし、未コミットの結果は空オブジェクトで確保する。
一意性競合を待った側は、確定した行を別のSQL文で読み直す。内容が同じなら同じ結果を返す。
最初の実行が失敗すればキー確保もロールバックするため、再送側が実行を引き継げる。空結果のままコミットする経路を作らない。
認証・認可は再送時にも行う。顧客向け取消と管理操作の権限を同じフラグで切り替えない。

在庫不足・不正遷移・重複処理・入力不正は業務エラーとして返す。DB例外を成功に変換しない。
デッドロック・直列化失敗(SQLSTATE 40P01/40001)は取引全体を同じキーで最大3回まで再試行し、解消しなければ競合を通知する（設計仮定）。
待ち時間は50ms・100msを基準に最大50msの乱数を加える。ロックタイムアウトは競合として通知し、無制限に再試行しない。
検証環境のlock_timeout=5秒・statement_timeout=15秒は試験用であり、本番値の確定ではない。

## 外部副作用

画像の変換・適正判定・新画像の保存を完了してから、短いDB取引でURLを変更する。
不適正な画像は保存せず、画像保管失敗時は書籍の登録・更新・棚入れを確定しない。
DB失敗時は今回の新画像を削除する補償を行う。DB成功後に旧画像を削除する。削除失敗は運用で再処理し、DB取引のロールバックで外部削除を取り消せるとは扱わない。
操作の再送は先に既存結果を確認し、新画像の二重作成を避ける。画像処理の完全な再送・補償実装は外部I/F設計の対象であり、本DB試験では検証しない。
送金・メール・配送業者呼出しのoutboxは、このスコープには存在しない。

## 照合・再構築・掃除

[照合SQL](sql/reconcile.sql)は同一スナップショットで不一致を列挙する。0行が正常。
現在状態の不一致に加え、在庫連続性・状態遷移・注文金額／明細欠落・初期取得・注文増減・棚入れ対応を検査する。
この照合は任意の改ざんを完全に検知する監査署名ではない。正本事実を無断変更しない運用とバックアップが必要である。

再構築は保守時間帯に書込みを停止し、[再構築SQL](sql/rebuild.sql)で対象表の書込みをロックする。
正本の検査に不一致があれば中断し、事実を勝手に修正しない。現在状態だけの破損なら在庫合計とイベント末端からUPSERTする。
再構築後に照合0行を確認して書込みを再開する。キャッシュの再構築はDBバックアップからの障害復旧の代替ではない。

[未ログインかごの掃除](sql/cleanup.sql)は運用者が基準時刻を指定して実行する。
`customer_subject IS NULL` と `updated_at < 基準時刻−1年` を同じDELETE条件にする。
ログイン統合・かご編集と同じ行のロックで競合し、待機後の条件再評価で有効なかごを消さない。認証済み顧客のかごは削除しない。
