# データ設計に関する要件の欠陥・確認事項と重大性評価

データの意味・所有・業務ルールと、その前提となる導入・検収条件をレビューする。
本書のRQ番号はレビュー用の識別子であり、合意済み要件のISSUE・RULE・D番号を置き換えない。
要件本文の修正や、追加機能への合意を表すものではない。設計との対応は[要件とデータモデルの照合・設計判断](requirements-model-reconciliation.md)を参照する。

## 1. 評価基準

重大性は、記述を異なる意味で実装した場合の業務影響で評価する。修正の手間や対応順序、現在の設計案に回避策があるかとは分ける。
発生確率の推測や、外部の評価規格への準拠を点数化したものではない。評価は本レビューの提案である。

| 重大性 | 評価の基準 | 確認・解消する時点 |
| --- | --- | --- |
| S1 致命的 | 金額・在庫・本人限定アクセスについて、必須の保護を成立させられない、または重大な損失へ直接つながる要件の欠陥 | 設計案の採用前。本レビューで該当と判断した指摘はない |
| S2 高 | 金額・原価・在庫の意味、主要業務の成立、導入・検収条件が分かれ、誤った解釈で必須機能や契約上の前提を損なう | 関連する基本設計・見積・受入条件の確定前 |
| S3 中 | データの保持範囲、操作結果、分類制約、期限判定等が分かれ、部分機能・運用・後工程の手戻りに影響する | 該当API・制約・運用手順・試験の確定前 |
| S4 低 | 強い規則に従えば整合して実装できるが、表現が揃わず誤読を招く | 要件文書の整合化時。新たな機能決定とは分ける |

「不整合」は同じ対象について文書間の主張が揃わないもの、「曖昧性」は複数の解釈が残るもの、「不備」は実装や受入判定に必要な境界条件がないものとする。
「不備候補」は運用で充足している可能性があり、機能追加の必要性をまだ断定しないものとする。
記述を整合させるだけでよい指摘と、業務判断が必要な指摘を、最右列で区別する。

## 2. 欠陥・確認事項の一覧

14件を重大性順に並べる。S2は7件、S3は6件、S4は1件。同じ重大性の中の番号順は対応優先度を表さない。
要件内の不整合はRQ-03・RQ-04・RQ-14、表現整備はRQ-13として区別し、それ以外は曖昧性・不備またはその候補として扱う。

## 3. 要件の欠陥に含めない設計側の問題

以下は要件に存在する欠陥として数えない。重大性は設計レビュー上の提案であり、RQの件数に加算しない。

| 設計側の項目 | 重大性・評価理由 | 必要な確認・対応 |
| --- | --- | --- |
| DS-01 概念図の未ログインかご | S3 中。DDLは顧客NULLを許すが設計概念図は必須関係のままで、後工程がどちらを正とするか迷う | RQ-03に対応する図の整合を取る。業務方針そのものを未決扱いに戻さない。DM-06・R04・F36 |
| DS-02 棚卸調整の概念が図で隠れる | S3 中。要件のSTOCK_ADJUSTMENTを一般のSTOCK_MOVEMENTに含め、対象行の意味や0..nが図だけでは分からない | DM-04・R13に沿って業務概念と上位概念の関係を明示する。別の物理表の新設が必須だとはしない |
| DS-03 設計の規模・保持量の影響が未評価 | S3 中。要件の12表という見当・3年後の件数に対し、設計は17表と履歴・冪等記録を持ち、保管・試験・運用負担を加える | 件数・容量・性能・工数の影響を評価する。差だけで要件違反・自動的な再見積の発動とはしない。機能・画面追加等の判断は[見積§5](../../estimate/scope-and-schedule.md)に従う |

BOOK_RECEIPT、ORDER_EVENT、OFFER_EVENT、現在状態、冪等記録の追加は、要件を実現する設計上の選択である。パターンを使ったため要件に欠陥がある、とは評価しない。
APIの認証・認可、画面、外部画像処理、50セッション性能、バックアップ復旧の未検証は、[検証範囲](validation/README.md#検証の限界)の問題であり、明記された要件そのものの欠陥とは区別する。
検索の既定順・ページ件数・未ログインかご掃除等、[12章](../../requirements/12-open-issues-and-risks.md)で基本設計へ明示的に委ねた事項も、未確定という理由だけでは欠陥に数えない。

## 4. 解消の判定

本書の指摘を記載しただけでは要件は解消しない。業務判断を伴うRQは店側の判断と具体例・境界値の期待結果、文書の整合化が必要なRQは対象箇所の一致を確認する。
確定した内容を要件の変更管理に反映し、照合文書のDM・R・Fと設計仮定、該当する受入条件を更新して初めて解消とする。
評価対象はデータの意味・所有・業務ルールと導入・検収条件である。全画面・全APIの網羅的な欠陥監査を対象とはしない。
