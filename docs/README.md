# Bob's Used Bookstore — 要件定義書

本書群は **要件定義工程の最終成果物** である。
顧客（店主）とベンダの間で、**何を作るか（スコープ）** と **いくらで・いつまでに作るか（金額・納期）**
を確定させるために必要十分な情報だけを持つ。

## 2. 詳細をどこまで書くか

要件定義書は **仕様書ではない。**
「何を作るのか」の像が顧客と一致し、規模が見積れるところまでを書き、それ以上は書かない。

| 本書に書くこと | 本書に書かないこと（基本設計以降で決める） |
| --- | --- |
| 機能の一覧と、各機能の目的・主要な入出力 | 画面項目の必須／任意、桁数、検証メッセージの文言 |
| 画面の一覧・遷移・主要画面の版面 | 全画面の版面確定、部品の配置、色・書体 |
| 主要エンティティと主要項目、件数の見当 | テーブル定義、列型、索引、正規化の判断 |
| 外部システムと、委ねる責務・失敗時の見え方 | API のパラメータ定義、リトライ・タイムアウト値 |
| 技術方式（言語・フレームワーク・実行基盤） | クラス構成、パッケージ構成、内部インタフェース |
| 業務ルールのうち **店が決めるもの**（税率・納期・しきい値） | それをどの層で守るか、実装上の制約 |
| 業務エラーとして扱う事象の**方針** | 個々の異常系の網羅、エラーコード体系 |

**「決めない」と決めたことも要件である。** 本書が沈黙している事項ではなく、
[12 課題とリスク](requirements/12-open-issues-and-risks.md) に明示的に置く。

## 3. 合意の状態

各文書の冒頭に状態を宣言する。

| `status` | 意味 |
| --- | --- |
| `agreed` | 要件定義完了レビューで顧客と合意済み。変更には変更管理手続きを要する |
| `proposed` | ベンダ提示。基本設計で確定させる |

要件定義中に出た判断は [決定事項一覧](requirements/decisions/README.md) に記録する。
重い判断（採らなかった案が金額・納期に効くもの）は `ADR-` として個別に残す。

## 4. 変更管理

`agreed` の記述を変えるときは、**スコープ・金額・納期への影響を評価してから**変える。
影響の判定基準と再見積の引き金は
[規模・体制・スケジュール §5](estimate/scope-and-schedule.md) にある。

## 5. 読む順

```
はじめて読む人       → glossary → 01 背景 → 02 スコープ → 06 画面
業務を確認する人     → 03 業務フロー → 05 業務ルール → 04 機能要件
見積を確認する人     → 02 スコープ → 04 機能要件 → 10 システム方式 → 規模・体制・スケジュール
基本設計に入る人     → 04 機能要件 → 06 画面 → 07 データ要件 → 12 課題
```
