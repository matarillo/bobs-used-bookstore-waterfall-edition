# ADR-0001 — オンライン決済を持たず、代金の授受をシステムの外に置く

| 項目 | 内容 |
| --- | --- |
| 決めた人 | 店主 |
| 影響する章 | [01 §5](../01-background-and-goals.md)、[02 §1](../02-scope.md)、[08 §3](../08-external-interfaces.md)、[11 §2](../11-constraints-and-assumptions.md) |
| 金額・納期への影響 | 決済機能・決済代行との連携・返金処理を見積から除外する |

## 決めたこと

注文の確定に決済を伴わせない。金額は算出して見せるが、**支払われた事実をシステムに記録しない。**
代金の授受は、店が実店舗で使ってきた運用（請求・振込・店頭受け渡し）でまかなう。

買取側の「支払う」も同じである。**支払った事実の記録**であって送金ではない。
支払方法・支払先を記録する項目を持たない。

## そう決めた理由

- 決済代行の契約・審査・手数料は、オンラインで注文が立つと分かる前に負うには重い固定費である。
- 実店舗の代金授受の運用がすでに回っており、そのまま使える。
- 決済を含めると、返金・与信・失敗時の巻き戻しが芋づるで必要になる。
  スコープが 2 倍近くに膨らみ、フェーズ 1 の納期に収まらない。

## 採らなかった案とその理由

| 案 | 採らなかった理由 |
| --- | --- |
| 決済代行（カード決済）を含める | 契約と実装の両方が重い。返品・返金の業務も同時に決めなければならず、要件定義が終わらない |
| 「支払済」フラグだけ設ける | 決済の裏付けなく手で立てるフラグは、店頭の帳簿と二重管理になり、かえって齟齬を生む |
| 銀行振込の消込のみ自動化する | 入出金明細との突合が必要で、決済代行より難度が高い |

## 再訪の条件

未収・支払齟齬のトラブルが常態化したとき（[RISK-02](../12-open-issues-and-risks.md)）。
**別契約として扱う。**

**顧客への説明が必須である。** 「注文した ＝ 支払った」ではないことを、
注文完了画面と注文詳細で明示する（[FR-CUS-08](../04-functional-requirements.md)）。
