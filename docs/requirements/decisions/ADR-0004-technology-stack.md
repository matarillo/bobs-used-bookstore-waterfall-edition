# ADR-0004 — 画面を React、業務ロジックを Spring Boot ＋ MyBatis、データ保管を PostgreSQL とする

| 項目 | 内容 |
| --- | --- |
| 決めた人 | ベンダ（店主の承認を得る） |
| 影響する章 | [10 システム方式](../10-system-architecture.md) 全体、[規模・体制・スケジュール](../../estimate/scope-and-schedule.md) |
| 金額・納期への影響 | **見積の前提そのものである。** 変更する場合は全面的な再見積を要する |

## 決めたこと

| 層 | 採用 |
| --- | --- |
| 画面 | **React**（TypeScript）。単一ページアプリケーションとして構築し、JSON API のみでサーバと通信する |
| 業務ロジック | **Spring Boot**（Java）。REST 風の JSON API を提供する |
| 永続化 | **MyBatis**。SQL を明示的に書く |
| データ保管 | **PostgreSQL**（マネージドサービス） |
| 実行基盤 | AWS。単一の実行単位で `CMP-SPA` の静的資材と `CMP-API` を提供する |

## そう決めた理由

- **React**: 管理画面の一覧・絞り込み・状態による操作の出し分けが多く、
  画面内で状態を持つ実装が向く。技術者の確保も容易である。
- **Spring Boot**: 業務ルール（[05 業務ルール](../05-business-rules.md)）を守る層を明確に分離でき、
  トランザクション境界を宣言的に扱える。注文確定のような「まとめて成立するかまとめて失敗するか」
  を要する処理に適する。
- **MyBatis**: この規模では SQL を隠すより見えるほうが保守しやすい。
  ダッシュボードの集計は SQL で書くほうが素直であり、
  集計と業務ロジックの境界がはっきりする。
- **PostgreSQL**: 金額を扱う列に十進の型を使える。マネージドサービスで運用手数が小さい。

## 採らないと決めたことと、その理由

| 案 | 採らなかった理由 |
| --- | --- |
| サーバ側で HTML を生成する方式 | 管理画面の絞り込みと出し分けが多く、画面遷移のたびに全体を描き直すと使い勝手が落ちる |
| JPA / Hibernate | 集計と一覧の照会が多い。生成される SQL の把握に手間がかかり、この規模では利点が出ない |
| 画面とサーバを別の実行単位に分ける | 運用費と運用手数が増える。[11 §3](../11-constraints-and-assumptions.md) の運用費上限に反する |
| マイクロサービス化 | 機能 32・テーブル 12 の規模で分割する理由がない |
| サーバレス（関数単位の実行） | 注文確定のトランザクション境界が扱いにくい。冷起動が [NFR-PERF-01](../09-non-functional-requirements.md) に効く |

## 再訪の条件

**再訪しない。** 実装開始後の技術方式の変更は、工程の全面的なやり直しを意味する。

想定規模（[11 §1](../11-constraints-and-assumptions.md)）を大きく超える見込みが立った場合のみ、
稼働後に構成の見直しを別途検討する。
