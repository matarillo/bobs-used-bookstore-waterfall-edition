# 決定事項

要件定義の読み合わせで確定した判断。**同じ議論を繰り返さないための記録である。**

決定はすでに本文へ反映されている。本書は「なぜそう決めたか」だけを持つ。

## 1. 決定事項一覧

| ID | 決めたこと | 理由 | 反映先 |
| --- | --- | --- | --- |
| `D-01` | **かごはログイン後、顧客に紐づける。** 未ログインの間はブラウザに置いたかご識別子で特定し、ログイン時に顧客のかごへ引き継ぐ | 家族で 1 台のブラウザを共有すると、別々にログインしてもかごが混ざる。中古書店の顧客層でこれは起きる。端末を替えるとかごが消えることも、常連客の離脱要因になる | [03 §1.1](../03-actors-and-business-flow.md), [10 §3](../10-system-architecture.md) |
| `D-02` | **検索は書名・著者・ISBN を部分一致で照合する。** 概要は対象としない。ジャンルとコンディションで絞り込める | 顧客がもっとも多く使う機能であり、照合対象が決まらなければ作れない。概要の全文検索は照合精度の調整に工数がかかるわりに、この蔵書規模では効きが薄い | [FR-CUS-02](../04-functional-requirements.md) |
| `D-03` | **業務エラーはその場で伝え、システムエラーだけをエラー画面へ送る。** 同時操作の競合（他のスタッフが先に処理した等）は業務エラーとする | 複数のスタッフが同じ一覧を見ながら作業するため、競合は日常的に起きる。理由の分からないエラー画面に落ちると業務が止まる | [06 §3](../06-screens.md), [FR-CMN-03](../04-functional-requirements.md) |
| `D-04` | **在庫切れの書籍はかごに入れられない。** 書籍詳細に在庫状態を表示する | 入れられるのに買えないのは、顧客が最も不満を持つ体験である。注文手続きまで進んで初めて分かるのは遅い | [FR-CUS-04](../04-functional-requirements.md), [RULE-STOCK-05](../05-business-rules.md) |
| `D-05` | **注文の取消ボタンは、取り消せる状態（受付待ち・受付済）のときだけ出す。** 確認ダイアログを挟む | 出荷済の注文に取消ボタンが出て、押すと失敗するのでは案内になっていない。取消は取り返しがつかないため、確認を要する | [FR-CUS-11](../04-functional-requirements.md), [05 §8.1](../05-business-rules.md) |
| `D-06` | **買取の進行を画面で補う。** 承認済のとき発送先住所と手順を案内し、却下時は理由を記録・表示し、承認待ちの申込を顧客が取り下げられる | 通知を持たない（[ADR-0002](ADR-0002-defer-notifications.md)）以上、画面が案内しなければ顧客は次に何をすべきか分からない。買取が止まる最大の原因になる | [FR-CUS-13](../04-functional-requirements.md), [FR-ADM-13](../04-functional-requirements.md), [RULE-OFFER-03](../05-business-rules.md) |
| `D-07` | **顧客に見せる金額をすべて税込合計に統一する** | 注文前に税抜、注文後に税込を見せると、顧客には「後から増えた」と映る。同じ買い物に二つの額が並ぶこと自体が問い合わせを生む | [RULE-ORDER-05](../05-business-rules.md) |
| `D-08` | **注文完了画面に注文番号・税込合計・納品予定日を表示する** | 顧客が店へ問い合わせるとき、何を伝えればよいかが分からない | [FR-CUS-08](../04-functional-requirements.md) |
| `D-09` | **仕入原価を書籍の必須項目とする。** 手入力の書籍にも入力を求める | 仕入原価を持たない書籍が売れると粗利が算出できない。[01 §4](../01-background-and-goals.md) の効果測定が成立しなくなる。「損をしていない」のではなく「分からない」状態が増えると、ダッシュボードの数字が信用されなくなる | [RULE-TRADE-07](../05-business-rules.md), [FR-ADM-07](../04-functional-requirements.md) |
| `D-10` | **在庫数の直接修正を「棚卸調整」として、理由と差分を記録する** | 棚卸の反映は実務上必要だが、注文による増減と手による修正が区別できないと、在庫が合わなくなったときに原因を追えない | [FR-ADM-09](../04-functional-requirements.md), [RULE-STOCK-07](../05-business-rules.md) |
| `D-11` | **書籍に非公開の印を設け、店頭の検索結果から外せるようにする** | 売り切れた本が検索結果に残り続けると、在庫切ればかりが並ぶ棚になる | [FR-ADM-10](../04-functional-requirements.md), [RULE-STOCK-08](../05-business-rules.md) |
| `D-12` | **「売れ筋」を累計の販売冊数の上位 4 件と定義する** | 期間で区切るには稼働直後のデータが足りない。累計なら初日から意味のある並びになる | [05 §9](../05-business-rules.md) |
| `D-13` | **データベースのバックアップを取る**（1 日 1 回・7 日保持、RPO 24 時間 / RTO 8 時間） | 買取の支払記録が失われると顧客との金銭トラブルに直結する。運用費の上限より優先する | [NFR-AVAIL-03](../09-non-functional-requirements.md) |
| `D-14` | **顧客側の一覧（自分の注文・住所・買取申込）にもページ送りを付ける** | 常連客の注文は 3 年で 100 件を超える。1 画面に並べ続けると使えなくなる | [06 §3](../06-screens.md) |
| `D-15` | **参照データ項目の名称の重複を許さない** | 同じ出版社が二重に登録されると、分類が分裂して検索も集計も合わなくなる | [FR-ADM-11](../04-functional-requirements.md) |
| `D-16` | **買取オファーの一覧に申込日での絞り込みを設ける** | ダッシュボードの「今月の申込」から辿ったとき、条件が効かなければ数字と一覧が一致しない | [FR-ADM-12](../04-functional-requirements.md) |
| `D-17` | **受領済からの却下を認める** | 現物が申告と違うことは実務上起きる。検分の結果で断れなければ、店は買いたくない本を買うことになる | [05 §8.2](../05-business-rules.md) |
| `D-18` | **希望買取価格の下限を 1 とする**（0 円での申込を受け付けない） | 0 円の買取は「引き取り」であって買取ではない。業務が違うものを同じ流れに混ぜない | [RULE-OFFER-02](../05-business-rules.md) |

## 2. 個別に理由を残す決定

採らなかった案が金額・納期に効くもの。

| ADR | 決めたこと |
| --- | --- |
| [ADR-0001](ADR-0001-defer-online-payment.md) | オンライン決済を持たず、代金の授受をシステムの外に置く |
| [ADR-0002](ADR-0002-defer-notifications.md) | 通知（メール等）を持たず、進行の確認を画面に限る |
| [ADR-0003](ADR-0003-defer-counter-offer.md) | 買取は顧客の希望額を承認／却下するだけとし、店側の査定額提示を持たない |
| [ADR-0004](ADR-0004-technology-stack.md) | 画面を React、業務ロジックを Spring Boot ＋ MyBatis、データ保管を PostgreSQL とする |
