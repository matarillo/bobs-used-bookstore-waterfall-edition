# ADR-0002 — 通知（メール等）を持たず、進行の確認を画面に限る

| 項目 | 内容 |
| --- | --- |
| 決めた人 | 店主とベンダ |
| 影響する章 | [01 §5](../01-background-and-goals.md)、[02 §1](../02-scope.md)、[08 §3](../08-external-interfaces.md) |
| 金額・納期への影響 | メール送信基盤の構築・テンプレート・配信管理を見積から除外する |

## 決めたこと

買取・注文の進行（承認、支払、出荷など）を顧客へ push で知らせる仕組みを持たない。
顧客は自分の申込一覧・注文一覧の画面で進行を確認する。

**そのぶん、画面が案内を担う**（[D-06](README.md)）。

- 買取が承認済（発送待ち）になったとき、**発送先住所と手順を画面に出す**
- 却下されたとき、**理由を画面に出す**

## そう決めた理由

- メール送達は片手間に足せる規模ではない。送信基盤の契約、送信ドメイン認証、
  バウンス処理、配信停止の扱いまで含めると、独立した一つの機能群になる。
- 初期の申込件数なら、滞留への声かけは店の運用（電話・店頭）で吸収できる。
- 通知を作るより先に、**画面が次の行動を案内していないこと**を直すほうが効く。
  発送先が分からない顧客は、通知が来ても本を送れない。

## 採らなかった案とその理由

| 案 | 採らなかった理由 |
| --- | --- |
| メール送信基盤を契約して状態遷移ごとに通知 | フェーズ 2 の納期に収まらない。送達率の運用が店の手に負えない |
| 画面内のお知らせ欄（ログイン後に未読を表示） | 送達の問題は避けられるが、「見に来ない顧客」には届かない。push と等価に解決しない。作るなら通知全体の設計と一緒に行う |

## 再訪の条件

承認済のまま現物が送られてこないオファーが滞留し始めたとき（[RISK-01](../12-open-issues-and-risks.md)）。
**別契約として扱う。**
